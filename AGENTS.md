# Workspace instructions (template — edit for your org)

Loaded into every session. The **Router** below decides what to load; everything long lives in the skill it routes to (each
skill's **Files** index says which file is read at which step). **Never put passwords, tokens or API keys here**: test logins
live only in `skills/qa-kit/targets.local.json` (git-ignored).

This file is the single source read by Codex and Antigravity directly, and by Claude Code through the `@AGENTS.md` import at
the top of `CLAUDE.md` (and `GEMINI.md`). Edit only here — never duplicate content into `CLAUDE.md`/`GEMINI.md`, or the three
tools drift apart. Mechanics that only Claude Code has (the Workflow tool, the Skill tool, agent spawning, hooks) are noted in
`CLAUDE.md`'s own section below the import, not here, since they don't apply to Codex/Antigravity.

## Router
Classify every request before acting: check the rows top to bottom; **the first row whose conditions all hold wins**. Go to its
**Target** after loading the **Load first** skill. A mixed request is split and each part routed on its own, in the same turn.
Skills a target needs at a later step are loaded at that step (its Files index says when); that is not a second match.

| # | Conditions (all must hold) | Target | Load first |
|---|---|---|---|
| R0 | The request matches a row of "Org router rows" in `rules/*.local.md` (org-only skills and needs) | that org row's target | — |
| R1 | A coordinator event: a workflow notification, a supervise flag, a stopped or failed agent, a pipeline failure or review finding on a wave's MR, the owner changing a rule mid-wave, a SessionStart kit line (git state, lint, retro) | `orchestrate` → its Events table | — |
| R2 | Kit friction or a kit change: a kit script, hook, rule or workflow failed, blocked wrongly or needed a workaround; or the request adds or changes a kit script, reference, template, skill, agent, workflow, rule or config key | `orchestrate` → "Change the kit" (edit this clone in place, commit, push) | — |
| R3 | See or explain how the kit fits together (what triggers what, why a file is or is not reached) | direct: open `<runtime>/cache/kit-flow.html` (regenerated by `kit-flow.py`) | `orchestrate` |
| R4 | A /dev-wave or /test-and-close finished (any outcome), the session-start nudge says signals piled up, or the owner asks for a kit retrospective | `/kit-retro` | `orchestrate` |
| R5 | Agents or a workflow stopped (usage limit, API timeout, RAM, owner) with work left in their worktrees | `/dev-wave` `mode: 'resume'` | `orchestrate` |
| R6 | Bug tasks raised by a QA run ("[Bug] … failed checks") are open | `/dev-wave` `mode: 'bugfix'`, one wave for every open bug | `orchestrate` |
| R7 | Review merge/pull requests that are already open (not the review inside a running /dev-wave) | `mr-reviewer` agent, one per author or area | — |
| R8 | Static audit of one module's code for bugs, performance or tech debt, without changing code | `tech-audit` | — |
| R9 | A person will test by hand: testing instructions or a tester guide are asked for | `qa-kit` → Guide steps G1-G3 | — |
| R10 | One deployed change, checked by you in this session (one screen or endpoint, no tester guide run) | direct, qa-kit rules | `qa-kit` |
| R11 | Deployed tasks on a test environment, each with a tester guide or how-to-test comment, are to be tested by agents | `/test-and-close` | `orchestrate` |
| R12 | Emulators, phones or the test APK outside a running /test-and-close: build the APK, create or reset lanes, a manual lease | `android-swarm` | — |
| R12b | Start, stop, deploy to, test or debug on a local environment (the one shared running instance of an app on this machine, `localEnv` in `kit.local.json`), or build an APK or run a task from it | `local-env` | — |
| R13 | Coding with more than 2 work items or tasks, one item spanning 2+ repos, or one large item (new feature or epic, migrations, many screens) | `/dev-wave` | `orchestrate` |
| R14 | Coding: one small change (one item in one repo: one screen, file or endpoint, a quick fix, a config edit) | direct, dev-kit rules | `dev-kit` |
| R15 | A question, an explanation, an analysis or a plan; no code change | direct | — |

- **Agent types** are spawned only through these targets: `dev-agent` by /dev-wave (one per brief area), `mr-reviewer` by
  /dev-wave (one per build agent) and R7, `qa-tester` and `qa-verifier` by /test-and-close. Each agent loads its skill first.
  Codex/Antigravity: the same agents exist as `.codex/agents/*.toml` and `.agents/agents/*.md` (generated by
  `skills/orchestrate/scripts/port-kit.py`), but there is no ported Workflow-tool equivalent to drive them through the phases
  below automatically — follow the matching procedure doc in `.codex/workflows/*.md` / `.agents/workflows/*.md` by hand.
- **Autonomous:** installing this kit is the standing opt-in for its workflows. Launch the routed workflow yourself without being
  asked or asking first, then say in one line what started (workflow, agents, repos) and why. An org that wants to be asked first
  says so in its org rules; then propose instead. A request already running in a workflow is never launched twice: add to it
  through the contracts file (R1). Size each workflow to the session's size guideline.
- **Local env (pre-staging):** with `localEnv` configured, dev agents deploy their branch to the env, test and `promote` it there
  (`local-env`, dev-kit step 6b) before merging. The env is local: deploying to it needs no person's yes; test environments still do.
- **Coding and testing in one request:** R13/R14 now; R11 (or R9) once a person has deployed. **Deploys, and merges into
  branches that deploy, always need a person's yes.**

## CLIs
Always check auth before using a CLI (never log in headlessly). Windows: resolve shims (`gws`, `gh`, `npx`, ...) with `shutil.which()`.

| CLI | Purpose | Auth check |
|-----|---------|------------|
| `glab` (or `gh`) | GitLab (GitHub): clone, push branches, open MRs/PRs | `glab auth status` / `gh auth status` |
| tracker | Tasks, comments, statuses: always through `skills/dev-kit/scripts/tracker.ps1` (`tracker.type` = clickup / github / gitlab / jira / none) | `tracker.ps1 view <id>` |
| `gws` (optional) | Google Workspace, only when `reports.type` is `gdocs` (tester guides and QA reports as Google Docs) | resolve with `shutil.which()` |
| `<your-cli>` | <purpose, e.g. cloud logs / observability queries> | `<auth check command>` |

## Org specifics (fill in)
- Org settings the scripts read (tracker, report output, git host, repos root, protected branches, ...): `skills/dev-kit/kit.local.json`
  (copy `kit.example.json`; keys in `skills/dev-kit/reference/configuration.md`).

- Products / repos (`<repo> — <one line>`), test environments (names only; URLs and logins in `targets.local.json`).
- Code conventions: path-scoped rules in `rules/` (examples in `examples/rules/`). Org-only references (database access,

  `kit.local.json` `localOnly` (kept out of git through `.git/info/exclude`).
- How to add any of these: `skills/orchestrate/reference/extending.md`.

## Not portable to Codex/Antigravity (stays Claude Code-only)
Verified against the installed CLIs (`codex` 0.157.0, `agy` 1.3.4) and each tool's own docs, 2026-10-13. These Claude Code
mechanics have no equivalent to port to, and are not simulated:
- The `SendMessage` guard hook (`orchestrate/scripts/guard-sendmessage.ps1`) — `SendMessage` is a Claude Code tool name; neither
  Codex nor Antigravity has a tool by that name to match a hook against.
- The agent board (`orchestrate/scripts/board.ps1`, duplicate-session detection) and `learn.ps1` signal capture — not wired into
  Codex's `spawn_agent`/`wait_agent` or Antigravity's `invoke_subagent` calls; the ported workflow procedure docs tell a human
  coordinator to use the board, but nothing enforces it automatically there.
- The `Skill` tool's name-triggered invocation and `kit-lint.py`'s router/graph validation only run inside Claude Code against
  this kit's own files.
- Antigravity's `tools:` allow-list on a subagent is left unset on purpose: its tool names (`view_file`, `run_command`, ...)
  don't map 1:1 from Claude's (`Read`, `Bash`, ...), and Antigravity's own docs warn a mismapped name can hang the subagent.
