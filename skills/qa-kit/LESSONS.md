# QA lessons — active rules (read before testing; ≤ 40 lines)
Newest first, one line each, `(n×)` = times seen. Fixed/old entries live in `HISTORY.md` (never read it for work).
UI gotchas for one product go under `## Project: <name> (target <target>)` (selectors, accounts to use or never touch, app login
steps) — never passwords; those live only in `targets.local.json`.

## General
- (2×) Lanes that share one admin user share the assistant chat list: give each lane its own session key, expect foreign files there, and delete only your own.
- (2×) Lead notes can widen scope mid-run: re-read lead-notes.md before each check and before releasing a seat; log added checks, never edit the guide in place.
- (25×) Defects are never notes: any 5xx, unexpected 4xx, stuck flow or unsaved data is FAIL (the note audit reclassifies it anyway). Silent 200-with-empty-data and a 5xx "fixed by a restart" need the saved request/response and an observability check; an unverified 5xx is FAIL.
- (27×) Evidence hygiene: save into the item folder with the standard name `CODE-ID_NN_slug`, setup evidence `<code>-<nn>-<slug>`; list only files that exist, relative names — never folders, helper scripts or absolute paths.
- (11×) Retests of a dev fix fail on the sibling path (list GET still 500, another state, edit round-trip, i18n keys: diff all keys against the default locale): exercise the full reported flow end to end (create/import, edit, cancel in locked/terminal states), not only the original error.
- Deployed? Before any FAIL run `deployed.ps1` for EVERY repo of the task (a consumer can be live while its producer is not). Undeployed fix = NOT_TESTED, never PASS_WITH_NOTE. A manual server deploy still reads NOT-DEPLOYED: trust the owner and say so. Two-stage web deploys (release pipeline to a deploy branch) go live only after the second pipeline. The test app can be redeployed mid-run: re-check the bundle version before finalising FAILs. A manual deploy the owner confirms counts as live: check it via an API marker (new field, version endpoint) before holding checks as NOT_TESTED. (5×)
- (3×) Layout fixes (scroll, max-height, panel drag bounds, a search field): test the smallest and largest supported viewports (e.g. 1366x768 and 1920x1080), measure header/panel bottoms vs innerHeight with real wheel scrolling only (scrollIntoView hides overflow:hidden clipping).
- (3×) Guide data drifts on shared environments (records completed, deleted, renamed): create your own data through the API and record it. Guides go stale when later work changes a screen: test the same intent on the current screen and say so (PASS_WITH_NOTE), not FAIL.
- (2×) Parallel items toggling a shared tenant setting cause transient 403s elsewhere: serialise those checks or record the setting state. Per-user preference checks use a secondary test user; keep one tenant/account with the feature OFF for "nothing else changed" (R) checks and never change it.
- (3×) LLM-driven checks (an AI decider/assistant) are intermittent: run each 5-14 times, record every run, keep the first and each deviating run as evidence. Re-run a deviating run before FAIL, and log its timestamp.
- (3×) Screenshot/canvas-capture checks: time them per screen (a long list took 77-128 s vs a 30 s tool timeout); don't blame host CPU without a re-run at low load. A guide scenario for a screen that does not host the component is reported, not silently moved. Wait until the table has pageSize rows before timing (lazy rows render late). A capture that blocks the page past its cap is FAIL, with the profile saved.
- (2×) Skipping an item: write the skip reason into run.json so the learn step can tell why.
- A server-side config check (model, temperature, fallback) is NOT_TESTED from the API lane: verify it in the deployed code plus its unit tests (run the repo's validation script directly when pytest isn't in the linked venv), name the env overrides you could not see, then close.
- A test environment's JWT signing key can differ from the repo config (re-signed tokens get 401): prove "refuses a token for another product" (several products sharing one auth service) by unit test or with the deployed key. A separately deployed service (e.g. a cloud function) may be undeployed: check first.
- Component-library overlays (e.g. ng-zorro): hover-open dropdowns need `hoverSel(page, selector)`; menu items render in `.cdk-overlay-container` (row "…" menus `.anticon-more`, items `.cdk-overlay-container li`); select options `.ant-select-dropdown:not(.ant-select-dropdown-hidden) .ant-select-item-option`; column filters `th .ant-table-filter-trigger` then `.cdk-overlay-container input`.
